LinkedList is a class in java.util that implements the List, Deque, and Queue interfaces. Internally, it's a doubly linked list — a sequence of nodes where each node holds:

the data (element)
a reference to the next node
a reference to the previous node
java
class Node<E> {
    E item;
    Node<E> next;
    Node<E> prev;
}

Unlike ArrayList (backed by a contiguous array), LinkedList elements are scattered in memory, connected only through these pointers. The LinkedList object itself keeps references to the first node and the last node, so it can efficiently insert/remove at both ends.

Class Declaration
java
public class LinkedList<E> extends AbstractSequentialList<E>
    implements List<E>, Deque<E>, Cloneable, java.io.Serializable

Because it implements Deque, a single LinkedList object can behave as a List, a Queue (FIFO), a Stack (LIFO), or a Deque (double-ended queue).

Key Characteristics
Ordered — maintains insertion order.
Allows duplicates and allows null elements.
Not synchronized (thread-unsafe by default; wrap with Collections.synchronizedList() if needed).
No random access — to reach the nth element it must walk from head or tail.
Implements RandomAccess? No — this is a common trick question. ArrayList implements RandomAccess, LinkedList does not.

Java Collections Framework (JCF) — Complete Interview Guide
What is JCF?
The Java Collections Framework is a unified architecture (a set of interfaces, classes, and algorithms) that Java provides to store, manage, and manipulate groups of objects (called "collections").

Before Java 2 (JDK 1.2), Java had things like Vector, Array, Hashtable — but they were all built separately, with no common interface. If you wanted to write code that worked with any kind of collection, you couldn't easily do it, because each class had its own methods with different names.

So Sun Microsystems introduced JCF to solve this problem: one common set of interfaces so that all collection classes behave in a predictable, interchangeable way.

Think of it like this analogy: imagine every store in a mall had a different way of billing — one uses a calculator, one uses paper, one uses an app. Now imagine the mall says "every store MUST use this one billing system." That's what JCF did for collections — it standardized how you store and access groups of data.

Why do we need it? (Interview favorite question)
Interviewers often ask: "Why was Collections Framework introduced?"

Answer with these points:

Before JCF, classes like Vector, Hashtable, Array had inconsistent methods — no common interface.
Code reusability — since all collections implement common interfaces (List, Set, Map), you can write generic code that works with any implementation.
Reduces programming effort — you don't need to write your own data structures (linked list, dynamic array, hash table) from scratch. JCF gives ready-made, tested, optimized implementations.
Increases performance — the implementations are highly optimized.
Provides interoperability between unrelated APIs — a standard way to pass collections around.
The Core Hierarchy (MUST know for interviews)
JCF has two main root interfaces:

                Iterable
                    |
                Collection
        /           |            \
      List          Set          Queue
       |          /    \            |
   ArrayList   HashSet  SortedSet  PriorityQueue
   LinkedList     |         |         Deque
   Vector    LinkedHashSet TreeSet      |
                                    ArrayDeque
                                    LinkedList


                  Map  (separate hierarchy, NOT a child of Collection)
                 /   \        \
             HashMap SortedMap  Hashtable
                |        |
          LinkedHashMap TreeMap
Important interview point: Map is NOT a part of the Collection interface. This trips up a lot of candidates. Map stores key-value pairs, so it doesn't fit the "group of individual objects" idea that Collection represents. But Map is still part of the "Collections Framework" as a whole (the umbrella term), even though it doesn't extend Collection.

1. List Interface
Definition: An ordered collection (also called a sequence) that allows duplicate elements. You access elements by their index (position), just like an array.

Key implementations:
a) ArrayList

Backed internally by a dynamic array (resizable array).
Fast random access — getting element at index i is O(1).
Slow insertion/deletion in the middle — because elements need to shift.
Not synchronized (not thread-safe by default).
Example:

java
List<String> fruits = new ArrayList<>();
fruits.add("Apple");
fruits.add("Banana");
fruits.add("Apple"); // duplicates allowed
System.out.println(fruits.get(0)); // Apple - fast access by index
b) LinkedList

Backed by a doubly linked list.
Fast insertion/deletion (O(1)) if you already have a reference to the node — no shifting needed.
Slow random access — O(n), because it has to traverse node by node.
Also implements the Deque interface, so it can work as a stack or queue too.
Example:

java
List<String> tasks = new LinkedList<>();
tasks.add("Task1");
tasks.add("Task2");
((LinkedList<String>) tasks).addFirst("UrgentTask"); // fast insert at front
c) Vector

Legacy class (from before JCF), later retrofitted to implement List.
Synchronized (thread-safe) but this makes it slower than ArrayList in single-threaded scenarios.
Rarely used today — mostly asked about in interviews for legacy knowledge.
Interview question: "ArrayList vs LinkedList — when would you use which?"

Use ArrayList when you do a lot of read/access operations (get by index).
Use LinkedList when you do a lot of insertions/deletions, especially at the beginning or middle.
2. Set Interface
Definition: A collection that does NOT allow duplicate elements. It models the mathematical "set" concept.

Key implementations:
a) HashSet

Backed internally by a HashMap.
No guaranteed order — elements can appear in any order when you iterate.
Very fast — O(1) average time for add, remove, contains.
Allows one null element.
Example:

java
Set<String> colors = new HashSet<>();
colors.add("Red");
colors.add("Blue");
colors.add("Red"); // duplicate - ignored, size stays 2
System.out.println(colors.size()); // 2
b) LinkedHashSet

Same as HashSet, but maintains insertion order using a linked list internally.
Slightly slower than HashSet due to maintaining order, but still very fast.
Example:

java
Set<String> visited = new LinkedHashSet<>();
visited.add("Page1");
visited.add("Page3");
visited.add("Page2");
// iteration order will be: Page1, Page3, Page2 (insertion order preserved)
c) TreeSet

Backed by a Red-Black Tree (a self-balancing binary search tree).
Elements are stored in sorted order (natural ordering, or a custom Comparator).
Operations are O(log n) — slower than HashSet but you get sorting for free.
Does NOT allow null (throws NullPointerException in most cases).
Example:

java
Set<Integer> numbers = new TreeSet<>();
numbers.add(50);
numbers.add(10);
numbers.add(30);
System.out.println(numbers); // [10, 30, 50] - automatically sorted
Interview question: "How does HashSet ensure no duplicates?"
Answer: Internally, HashSet uses a HashMap where your element becomes the key, and a dummy constant value (PRESENT) is the value. When you call add(), it checks hashCode() first to find the bucket, then uses equals() to check if an identical element already exists in that bucket. If equals() returns true, it's treated as a duplicate and not added. This is why overriding hashCode() and equals() correctly is critical when you store custom objects in a HashSet.

3. Queue Interface
Definition: Designed to hold elements before processing, typically in FIFO (First-In-First-Out) order — like a real-world queue/line.

Key implementations:
a) PriorityQueue

Elements are NOT processed FIFO — instead, they're ordered by priority (natural ordering or custom Comparator).
Backed internally by a binary heap.
The element with the highest priority (smallest value, by default) comes out first.
Example:

java
Queue<Integer> pq = new PriorityQueue<>();
pq.add(30);
pq.add(10);
pq.add(20);
System.out.println(pq.poll()); // 10 - smallest element comes out first
b) Deque (Double-Ended Queue)

Allows insertion and removal from both ends (front and back).
Can be used as a Stack (LIFO) or a Queue (FIFO).
ArrayDeque is the common implementation — faster than Stack class and LinkedList when used as a stack.
Example:

java
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1); // add to front
stack.push(2);
stack.push(3);
System.out.println(stack.pop()); // 3 - Last In First Out behavior
Interview tip: Interviewers often ask "Why is ArrayDeque preferred over Stack class?"

The legacy Stack class extends Vector, making it synchronized and slower.
ArrayDeque is not synchronized (faster for single-threaded use) and is the recommended modern way to implement stack behavior.
4. Map Interface (separate from Collection, but part of JCF)
Definition: Stores data as key-value pairs. Keys are unique; values can repeat.

Key implementations:
a) HashMap

Most commonly used Map implementation.
No guaranteed order.
Allows one null key and multiple null values.
O(1) average time complexity for get/put.
Internally: array of "buckets" (called a table), each bucket holds a linked list (or a balanced tree, if the bucket gets too large — since Java 8, buckets convert to a Red-Black Tree if they exceed 8 entries, to avoid worst-case O(n) lookup).
Example:

java
Map<String, Integer> ages = new HashMap<>();
ages.put("Alice", 25);
ages.put("Bob", 30);
ages.put("Alice", 26); // overwrites the earlier value for the same key
System.out.println(ages.get("Alice")); // 26
b) LinkedHashMap

Like HashMap but maintains insertion order (or optionally, access order — useful for building an LRU cache).
Example:

java
Map<String, Integer> cache = new LinkedHashMap<>();
cache.put("a", 1);
cache.put("c", 3);
cache.put("b", 2);
// iteration order: a, c, b (insertion order)
c) TreeMap

Backed by a Red-Black Tree.
Keys are stored in sorted order.
O(log n) for get/put.
Example:

java
Map<String, Integer> scores = new TreeMap<>();
scores.put("Charlie", 85);
scores.put("Alice", 90);
scores.put("Bob", 75);
System.out.println(scores); // {Alice=90, Bob=75, Charlie=85} - sorted by key
d) Hashtable

Legacy class (predates JCF).
Synchronized, so thread-safe but slower.
Does NOT allow any null key or null value (throws NullPointerException).
Interview question: "HashMap vs Hashtable vs ConcurrentHashMap?"

Feature	HashMap	Hashtable	ConcurrentHashMap
Thread-safe	No	Yes (whole map locked)	Yes (segment/bucket-level locking)
Null keys/values	1 null key, multiple null values	Not allowed	Not allowed
Performance	Fast	Slow (due to full locking)	Fast even with concurrency
Introduced in	JDK 1.2	JDK 1.0 (legacy)	JDK 1.5
This is a VERY common interview question, so know this table well.

Iterator and Iterable (important interview topic)
Every Collection extends Iterable, which means every collection can be traversed using an Iterator.

java
List<String> names = new ArrayList<>();
names.add("John");
names.add("Jane");

Iterator<String> it = names.iterator();
while (it.hasNext()) {
    String name = it.next();
    if (name.equals("Jane")) {
        it.remove(); // safe way to remove while iterating
    }
}
Interview question: "Why can't you remove an element from a List directly while using a for-each loop?"

Answer: If you do this:

java
for (String name : names) {
    if (name.equals("Jane")) {
        names.remove(name); // throws ConcurrentModificationException
    }
}
This throws ConcurrentModificationException. This is because the for-each loop internally uses an Iterator, and the Iterator keeps a modCount (modification count) to detect if the collection was changed while iterating. Directly calling list.remove() changes the modCount outside the iterator's control, so on the next next() call, it detects the mismatch and throws the exception.

The fix: use Iterator.remove() (as shown above) which properly updates the internal state, or use removeIf():

java
names.removeIf(name -> name.equals("Jane"));
Comparable vs Comparator (frequently asked together with JCF)
Both are used to define sorting logic for objects in collections like TreeSet, TreeMap, or when using Collections.sort().

Comparable — defines the natural/default ordering. The class itself implements this.

java
class Student implements Comparable<Student> {
    int marks;
    Student(int marks) { this.marks = marks; }
    
    @Override
    public int compareTo(Student other) {
        return this.marks - other.marks; // ascending order by marks
    }
}
Comparator — defines a custom/external ordering. Useful when you want multiple ways to sort, or you can't modify the class.

java
List<Student> students = new ArrayList<>();
Collections.sort(students, new Comparator<Student>() {
    public int compare(Student s1, Student s2) {
        return s2.marks - s1.marks; // descending order
    }
});

// Or with lambda (Java 8+):
students.sort((s1, s2) -> s2.marks - s1.marks);
Interview one-liner to remember: "Comparable is implemented BY the class to define its natural order (compareTo method); Comparator is a SEPARATE class used to define custom orderings from outside (compare method)."

Fail-Fast vs Fail-Safe Iterators (advanced but commonly asked)
Fail-Fast iterators (used by ArrayList, HashMap, HashSet, etc.): Throw ConcurrentModificationException immediately if the collection is modified while iterating. They work directly on the original collection.
Fail-Safe iterators (used by CopyOnWriteArrayList, ConcurrentHashMap): Work on a cloned copy of the collection, so modifications during iteration don't throw exceptions. Downside: the iterator might not reflect the most recent changes (data could be slightly stale), and cloning has a memory/performance cost.

Collection Interface, List Interface, and List Implementations — Deep Dive for Interviews
1. What is the Collection Interface?
Let's start from the very top of the hierarchy.

Collection is the root interface of the entire Java Collections Framework (except Map, which is separate). It represents a group of individual objects, called "elements."

Think of Collection as a blueprint — a contract that says "any class that wants to be called a collection must provide these basic abilities":

add(element) — add something to the group
remove(element) — remove something
size() — how many elements are there
contains(element) — check if something exists in the group
isEmpty() — check if the group is empty
iterator() — get a way to loop through the elements
clear() — remove everything
Important point for interviews: You can NEVER create an object of Collection directly, because it's an interface (no implementation, just method signatures). It's always used through its child interfaces like List, Set, or Queue, and their concrete classes like ArrayList, HashSet, etc.

Think of it like the word "vehicle." You can't buy a "vehicle" — you buy a specific type: a car, a bike, a truck. Similarly, you can't create a "Collection" — you create a specific type: ArrayList, HashSet, LinkedList, etc. But all of them share the common behavior defined by Collection.

java
// This is NOT allowed:
// Collection c = new Collection(); // ERROR - interface can't be instantiated

// This IS allowed - using the interface as a reference type:
Collection<String> c = new ArrayList<>(); // valid - polymorphism
c.add("Hello");
c.add("World");
System.out.println(c.size()); // 2
This last example is actually a very important coding-to-interface practice that interviewers look for — declaring the variable type as the interface (Collection or List) rather than the concrete class (ArrayList). This way, your code becomes flexible: tomorrow if you want to switch from ArrayList to LinkedList, you only change the right-hand side, not every line of code that uses the variable.

2. What is the List Interface?
List is a child interface of Collection. It adds extra features on top of what Collection provides.

The two defining characteristics of List:
It maintains insertion order. Whatever order you add elements in, that's the order they stay in (unless you manually sort or shuffle them). This is different from Set, where order is often not guaranteed.
It allows duplicate elements. You can add "Apple" three times to a List, and all three will exist as separate entries.
It is index-based — every element has a position (starting from 0), just like an array. This means List gives you extra methods that plain Collection doesn't have, such as:
get(int index) — get element at a specific position
set(int index, element) — replace element at a position
add(int index, element) — insert at a specific position
indexOf(element) — find the position of an element
remove(int index) — remove element at a specific position
java
List<String> names = new ArrayList<>();
names.add("Ravi");
names.add("Priya");
names.add("Ravi"); // duplicate allowed
System.out.println(names); // [Ravi, Priya, Ravi]
System.out.println(names.get(1)); // Priya - accessing by index
names.set(1, "Anita"); // replace Priya with Anita
System.out.println(names); // [Ravi, Anita, Ravi]
Interview one-liner: "List is an ordered collection that allows duplicates and provides index-based access to elements."

Now let's go through each implementation of List in complete depth, because this is where most interview questions come from.

3. ArrayList — Detailed Explanation
How it works internally
ArrayList is backed by a dynamic array. Now, you might know that a normal array in Java has a fixed size — once you create int[] arr = new int[5], you can never make it hold 6 elements; you'd have to create a whole new array.

ArrayList solves this problem. Internally, it still uses a plain array (Object[]), but it manages resizing automatically for you.

Here's exactly what happens step by step:

When you create new ArrayList<>() with no arguments, Java creates an internal array with default capacity (historically 10, though in modern Java it starts empty and allocates 10 on the first add()).
When you call add(), the element goes into the next available slot in that internal array.
When the internal array becomes full and you try to add one more element, ArrayList does this:
Creates a new, bigger array (typically 1.5x the old size — the exact formula is newCapacity = oldCapacity + (oldCapacity >> 1), meaning old size + half of old size).
Copies all the elements from the old array into the new array.
The old array becomes eligible for garbage collection.
This resizing operation is expensive (it's an O(n) operation because copying happens), but it doesn't happen on every add() — only when the array is full. On average, insertion is still considered O(1) amortized (meaning if you average the cost of many additions, most are fast, and just occasionally you pay the resize cost).
Time complexities (very commonly asked)
Operation	Time Complexity	Why
get(index)	O(1)	Array supports direct indexed access — jumps straight to memory location
add(element) at the end	O(1) amortized	Usually just placed in next slot; occasionally triggers resize
add(index, element) in the middle	O(n)	All elements after that index must shift right by one position
remove(index)	O(n)	All elements after that index must shift left by one position
contains(element)	O(n)	Has to check every element one by one (linear search)
Example showing the shifting cost:
java
List<Integer> list = new ArrayList<>();
list.add(1);
list.add(2);
list.add(3);
list.add(4);
// list is [1, 2, 3, 4]

list.add(1, 99); // insert 99 at index 1
// Internally: elements 2, 3, 4 all shift one position to the right
// list becomes [1, 99, 2, 3, 4]

list.remove(0); // remove element at index 0 (which is 1)
// Internally: all remaining elements shift one position to the left
// list becomes [99, 2, 3, 4]
When to use ArrayList
Use it when:

You mostly read/access elements (a lot of get() calls).
You mostly add elements at the end (not the beginning or middle).
You don't need thread-safety.
Is ArrayList thread-safe?
No. If multiple threads modify an ArrayList at the same time without external synchronization, you can get unpredictable behavior or ConcurrentModificationException. If you need a thread-safe list, you'd use Collections.synchronizedList(new ArrayList<>()) or CopyOnWriteArrayList.

4. LinkedList — Detailed Explanation
How it works internally
LinkedList is implemented as a doubly linked list. This means it does NOT use a single continuous array in memory. Instead, it consists of individual objects called nodes, and each node has three parts:

The actual data (the element you stored)
A reference (pointer) to the next node
A reference (pointer) to the previous node
So visually, it looks like this:

null <- [prev|data|next] <-> [prev|data|next] <-> [prev|data|next] -> null
           Node 1                Node 2                Node 3
The LinkedList object itself just keeps track of two things: a reference to the first node (head) and a reference to the last node (tail).

Why insertion/deletion is fast in LinkedList
If you want to insert a new node at the beginning or end, you don't need to shift anything — you just:

Create the new node.
Update a couple of pointers (the new node's next/prev, and the old head/tail's next/prev).
This is O(1) — constant time — regardless of how many elements are already in the list, as long as you're inserting at the beginning, end, or you already have a reference to the node (like when using an Iterator or ListIterator to insert while traversing).

Why random access is slow in LinkedList
If you want to get(index) an element in the middle, there's no way to "jump" to it like in an array. You have to start from the head (or tail, whichever is closer) and follow the next (or prev) pointers one by one until you reach the desired position. This makes get(index) an O(n) operation.

Time complexities
Operation	Time Complexity	Why
get(index)	O(n)	Must traverse node by node from head or tail
addFirst() / addLast()	O(1)	Just updates head/tail pointers, no shifting
add(index, element) in the middle	O(n)	Still needs to traverse to find the position first, even though the actual insertion is O(1)
remove(index)	O(n)	Same reason — traversal cost dominates
contains(element)	O(n)	Linear search, same as ArrayList
Example:
java
LinkedList<String> tasks = new LinkedList<>();
tasks.add("Task A");
tasks.add("Task B");
tasks.add("Task C");

tasks.addFirst("Urgent Task"); // O(1) - just adjusts head pointer
// tasks: [Urgent Task, Task A, Task B, Task C]

tasks.addLast("Final Task"); // O(1) - just adjusts tail pointer
// tasks: [Urgent Task, Task A, Task B, Task C, Final Task]

tasks.removeFirst(); // O(1)
System.out.println(tasks); // [Task A, Task B, Task C, Final Task]
LinkedList also implements Deque and Queue
Because of its node-based structure with easy access to both ends, LinkedList can behave like a Queue (FIFO) or a Stack (LIFO), or a Deque (both ends). This is a special and important interview point — LinkedList implements the List interface AND the Deque interface simultaneously.

java
LinkedList<Integer> stack = new LinkedList<>();
stack.push(10); // acts like a stack
stack.push(20);
stack.push(30);
System.out.println(stack.pop()); // 30 - LIFO behavior

Queue<Integer> queue = new LinkedList<>();
queue.offer(1); // acts like a queue
queue.offer(2);
queue.offer(3);
System.out.println(queue.poll()); // 1 - FIFO behavior
When to use LinkedList
Use it when:

You do a lot of insertions/deletions at the beginning or in the middle (especially using an iterator).
You need it to behave like a Queue, Deque, or Stack.
You don't need fast random access by index.
Memory consideration (often asked)
LinkedList uses more memory per element than ArrayList, because each node needs to store two extra references (next and prev) along with the data, whereas ArrayList just stores the raw data in a compact array.

5. ArrayList vs LinkedList — Direct Comparison (classic interview question)
Feature	ArrayList	LinkedList
Internal structure	Dynamic array	Doubly linked list
Random access (get(i))	Fast — O(1)	Slow — O(n)
Insertion/Deletion at ends	O(1) amortized, but end-shifting in middle is O(n)	O(1) at both ends
Insertion/Deletion in middle	O(n) — needs shifting	O(n) — needs traversal, but no shifting
Memory usage	Less (compact array)	More (extra pointers per node)
Implements Deque?	No	Yes
Best used for	Frequent read/search operations	Frequent insert/delete operations
How to answer this in an interview: "If my application does a lot of searching and reading data by index, I'd choose ArrayList because array-based indexing gives O(1) access. But if my application frequently inserts or removes elements, especially at the front or in bulk, I'd lean toward LinkedList because it avoids the costly shifting that ArrayList requires."

6. Vector — Detailed Explanation
What is it?
Vector is one of the oldest classes in Java, existing even before the Collections Framework was introduced in JDK 1.2. When JCF was created, Vector was "retrofitted" (modified) to implement the List interface, so it could fit into the new framework.

How it works internally
Just like ArrayList, Vector is also backed by a dynamic array. The internal mechanics of growing the array when it's full are almost identical to ArrayList.

Key difference in growth strategy:

ArrayList grows by 1.5x its current size when full.
Vector grows by 2x (doubles) its current size when full, by default (though you can specify a custom increment).
The BIG difference: Synchronization
This is the #1 interview point about Vector. Almost every single method in Vector (add(), get(), remove(), etc.) is marked with the synchronized keyword.

What does synchronized mean here? It means only one thread can execute that method on a given Vector object at a time. If Thread A is currently running vector.add(), Thread B has to wait until Thread A finishes, even if Thread B just wants to do a harmless get().

java
public synchronized boolean add(E e) {
    // ... adds element
}
This makes Vector thread-safe — safe to use when multiple threads access the same Vector object simultaneously without external synchronization code. ArrayList, in contrast, is NOT thread-safe by default.

The cost of this safety
Synchronization isn't free. Every single method call has to acquire a "lock" before running and release it afterward, even if there's only ONE thread using the Vector (i.e., in a normal, non-multithreaded program). This locking/unlocking overhead makes Vector noticeably slower than ArrayList in single-threaded scenarios — which is most typical use cases.

Example:
java
Vector<String> vector = new Vector<>();
vector.add("A");
vector.add("B");
vector.add("C");
System.out.println(vector); // [A, B, C]
System.out.println(vector.get(0)); // A
Syntactically, it looks almost identical to ArrayList — that's the point of the common List interface. But under the hood, its thread-safety behavior is very different.

Why is Vector considered "legacy" and rarely recommended today?
Because Java now provides better alternatives for thread-safe lists:

Collections.synchronizedList(new ArrayList<>()) — wraps an ArrayList to make it synchronized, giving you more flexibility.
CopyOnWriteArrayList (from java.util.concurrent) — a modern thread-safe list, ideal when you have many reads and few writes; it creates a fresh copy of the underlying array whenever a write happens, so reads never need locking.
Interview one-liner: "Vector is a legacy, synchronized version of a dynamic array. It's thread-safe but slower than ArrayList due to synchronization overhead on every method call. In modern Java, we prefer ArrayList for single-threaded use, or CopyOnWriteArrayList / Collections.synchronizedList() for multi-threaded use."

7. Stack — Detailed Explanation
What is it?
Stack is a class that represents the classic LIFO (Last-In-First-Out) data structure — imagine a physical stack of plates. You can only add a plate to the top, and you can only remove the plate from the top. The plate you put in last is the first one you take out.

The surprising interview fact about Stack
Here's something that surprises a lot of people, and interviewers LOVE asking about it:

Stack extends Vector.

java
public class Stack<E> extends Vector<E> {
    // ...
}
This means Stack inherits all of Vector's characteristics — including synchronization (thread-safety) and all of Vector's methods like get(index), add(index, element), insertElementAt(), etc.

Why this is considered a design flaw
Interviewers often ask: "What's wrong with the Stack class in Java?"

The problem is: a proper stack data structure should ONLY allow operations at the top (push, pop, peek). But because Stack extends Vector, it also inherits methods that let you insert or access elements anywhere in the middle — completely breaking the LIFO discipline that a stack is supposed to enforce!

java
Stack<Integer> stack = new Stack<>();
stack.push(1);
stack.push(2);
stack.push(3);

// This should NOT be allowed in a "pure" stack, but Java allows it 
// because Stack inherits Vector's methods:
stack.add(0, 99); // inserts 99 at the very bottom! Breaks LIFO logic
System.out.println(stack); // [99, 1, 2, 3]
This is exactly why, in modern Java, it's recommended to use ArrayDeque instead of Stack when you need stack-like behavior:

java
Deque<Integer> stack = new ArrayDeque<>();
stack.push(1);
stack.push(2);
stack.push(3);
System.out.println(stack.pop()); // 3 - proper LIFO, and ArrayDeque doesn't expose 
                                   // methods that would break stack discipline the same way
Stack's core methods:
Method	What it does
push(element)	Adds element to the top of the stack
pop()	Removes AND returns the top element. Throws EmptyStackException if stack is empty
peek()	Returns the top element WITHOUT removing it. Also throws EmptyStackException if empty
empty()	Returns true if the stack has no elements
search(element)	Returns the 1-based position of an element from the top; returns -1 if not found
Full example:
java
Stack<String> plates = new Stack<>();
plates.push("Plate1");
plates.push("Plate2");
plates.push("Plate3");
System.out.println(plates); // [Plate1, Plate2, Plate3]

System.out.println(plates.peek()); // Plate3 - just looks at top, doesn't remove

System.out.println(plates.pop()); // Plate3 - removes and returns top
System.out.println(plates); // [Plate1, Plate2]

System.out.println(plates.search("Plate1")); // 2 - it's the 2nd element from the top
System.out.println(plates.empty()); // false
Why Stack is slow (same reason as Vector)
Since Stack extends Vector, every method call (push, pop, peek) is synchronized. So even in a single-threaded program, you pay the locking overhead unnecessarily.

Interview one-liner: "Stack is a legacy class that extends Vector, giving it LIFO methods (push, pop, peek) but also inheriting Vector's synchronization overhead and, problematically, its index-based methods that can break stack discipline. Modern Java code should prefer ArrayDeque for stack behavior, since it's faster (unsynchronized) and doesn't expose those unwanted index-based operations."
